Reporte diario de trámites pendientes por correo

COUNT Database Mail sp_send_dbmail SQL Server Agent
1 Enunciado del ejercicio
Crear un procedimiento almacenado que consulte diariamente la cantidad de trámites pendientes y envíe un correo electrónico con el resumen.
2 Script en T-SQL
SP_ReporteTramitesPendientes.sql
CREATE OR ALTER PROCEDURE Tramite.SP_ReporteTramitesPendientes
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @Cantidad INT;
    DECLARE @Asunto   NVARCHAR(200);
    DECLARE @Cuerpo   NVARCHAR(MAX);
    DECLARE @Fecha    VARCHAR(20) = CONVERT(VARCHAR(20), GETDATE(), 103);

    BEGIN TRY
        SELECT @Cantidad = COUNT(*)
        FROM Tramite.Tramite
        WHERE Estado = 'Pendiente';

        SET @Asunto = CONCAT(N'Reporte diario de trámites pendientes - ', @Fecha);

        SET @Cuerpo = CONCAT(
            N'Buenos días,', CHAR(13)+CHAR(10), CHAR(13)+CHAR(10),
            N'Al día de hoy (', @Fecha, N') existen ', @Cantidad,
            N' trámite(s) pendiente(s) de atención.', CHAR(13)+CHAR(10), CHAR(13)+CHAR(10),
            N'Este es un mensaje generado automáticamente por el sistema de monitoreo.'
        );

        EXEC msdb.dbo.sp_send_dbmail
            @profile_name = 'PerfilMonitoreo',
            @recipients   = 'supervision@empresa.com',
            @subject      = @Asunto,
            @body         = @Cuerpo,
            @body_format  = 'TEXT';
    END TRY
    BEGIN CATCH
        -- El fallo del envío no debe interrumpir el proceso de monitoreo
        PRINT CONCAT('Error al enviar el reporte: ', ERROR_MESSAGE());
    END CATCH
END;
GO

-- Programación en SQL Server Agent (ejecución diaria a las 07:00 a.m.)
EXEC msdb.dbo.sp_add_job @job_name = N'Job_ReporteTramitesPendientes';
EXEC msdb.dbo.sp_add_jobstep
    @job_name = N'Job_ReporteTramitesPendientes',
    @step_name = N'Ejecutar reporte',
    @subsystem = N'TSQL',
    @command = N'EXEC Tramite.SP_ReporteTramitesPendientes;',
    @database_name = N'GradosTitulos';
EXEC msdb.dbo.sp_add_schedule
    @schedule_name = N'DiarioMañana',
    @freq_type = 4,            -- diario
    @freq_interval = 1,
    @active_start_time = 070000;
EXEC msdb.dbo.sp_attach_schedule
    @job_name = N'Job_ReporteTramitesPendientes',
    @schedule_name = N'DiarioMañana';
EXEC msdb.dbo.sp_add_jobserver
    @job_name = N'Job_ReporteTramitesPendientes';
GO
3 Justificación técnica

COUNT(*) resuelve la agregación directamente en el motor, evitando traer filas al cliente solo para contarlas. El procedimiento se encapsula para poder invocarse tanto manualmente como desde un job de SQL Server Agent, separando la lógica de negocio (consulta) de la lógica de notificación (correo). sp_send_dbmail se ejecuta contra msdb, que es donde reside Database Mail, y utiliza un perfil de correo previamente configurado en lugar de credenciales SMTP embebidas en el script. CREATE OR ALTER hace el despliegue idempotente: el mismo script puede volver a ejecutarse sin necesidad de un DROP previo.

4 Buenas prácticas aplicadas
  • SET NOCOUNT ON para evitar mensajes de conteo de filas innecesarios en la salida.
  • Separación de responsabilidades: un job de Agent programa la ejecución; el procedimiento solo contiene lógica.
  • Manejo defensivo del envío de correo con TRY/CATCH, para que un fallo de Database Mail no interrumpa el job.
  • Uso de CONCAT con literales Unicode (N'...') para evitar problemas de codificación en tildes y ñ.
  • Nombres de perfil y destinatarios como configuración, no como valores hardcodeados dispersos en el código.
Qué observa este proyecto
Tramite.Tramite → Estado = 'Pendiente' Frecuencia: diaria 07:00 a.m. Canal de salida: correo (Database Mail)

Auditoría automática de errores en SP_RegistrarTramite

TRY / CATCH ERROR_MESSAGE() ERROR_NUMBER() ERROR_LINE()
1 Enunciado del ejercicio
Registrar automáticamente en una tabla de auditoría todos los errores producidos durante la ejecución del procedimiento Tramite.SP_RegistrarTramite.
2 Script en T-SQL
Auditoria_SP_RegistrarTramite.sql
-- Tabla de auditoría de errores
CREATE TABLE Tramite.AuditoriaErrores
(
    IdError        INT IDENTITY(1,1)  PRIMARY KEY,
    NombreProceso  NVARCHAR(128)      NOT NULL,
    NumeroError    INT                NOT NULL,
    MensajeError   NVARCHAR(2048)     NOT NULL,
    LineaError     INT                NULL,
    Severidad      INT                NULL,
    Estado         INT                NULL,
    UsuarioBD      NVARCHAR(128)      NOT NULL DEFAULT SUSER_SNAME(),
    FechaError     DATETIME2          NOT NULL DEFAULT SYSDATETIME()
);
GO

CREATE OR ALTER PROCEDURE Tramite.SP_RegistrarTramite
    @IdSolicitante INT,
    @TipoTramite   VARCHAR(50),
    @Descripcion   NVARCHAR(500)
AS
BEGIN
    SET NOCOUNT ON;

    BEGIN TRY
        BEGIN TRANSACTION;

        INSERT INTO Tramite.Tramite (IdSolicitante, TipoTramite, Descripcion, Estado, FechaRegistro)
        VALUES (@IdSolicitante, @TipoTramite, @Descripcion, 'Pendiente', GETDATE());

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF XACT_STATE() <> 0
            ROLLBACK TRANSACTION;

        INSERT INTO Tramite.AuditoriaErrores
            (NombreProceso, NumeroError, MensajeError, LineaError, Severidad, Estado)
        VALUES
            (N'Tramite.SP_RegistrarTramite', ERROR_NUMBER(), ERROR_MESSAGE(),
             ERROR_LINE(), ERROR_SEVERITY(), ERROR_STATE());

        THROW; -- se conserva el error original para la capa que invocó el SP
    END CATCH
END;
GO
3 Justificación técnica

El bloque TRY/CATCH aísla la operación de inserción de negocio de su manejo de fallos. Antes de hacer ROLLBACK se valida XACT_STATE(), porque si la transacción quedó en estado "no confirmable" (-1) un ROLLBACK directo sin esa verificación puede generar un error adicional. Las funciones ERROR_NUMBER(), ERROR_MESSAGE(), ERROR_LINE(), ERROR_SEVERITY() y ERROR_STATE() solo son válidas dentro del CATCH y capturan el diagnóstico completo del error tal como lo vio el motor. Finalmente, THROW relanza el error original hacia la aplicación cliente después de auditarlo, en vez de "tragárselo" silenciosamente.

4 Explicación de las buenas prácticas utilizadas
  • Verificación de XACT_STATE() antes de cualquier ROLLBACK.
  • Uso de THROW en vez de RAISERROR, ya que preserva número, severidad y línea originales del error.
  • DATETIME2 y SUSER_SNAME() por defecto en la tabla de auditoría, para trazabilidad temporal y de usuario sin depender de que el SP los provea.
  • El error nunca se pierde: se audita y además se propaga, cumpliendo doble función (registro + notificación al llamador).
  • Transacción explícita y acotada solo a la operación de escritura, minimizando el tiempo de bloqueo.
Qué observa este proyecto
Tramite.SP_RegistrarTramite Errores de inserción / validación Destino: Tramite.AuditoriaErrores

Monitoreo del crecimiento del archivo de log

sys.database_files sys.dm_db_log_space_usage SQL Server Agent Database Mail
1 Enunciado del ejercicio
Diseñar un sistema que monitoree el crecimiento del archivo de log de la base de datos y genere una alerta cuando supere el 80 % del tamaño configurado.
2 Script en T-SQL
SP_MonitorearCrecimientoLog.sql
CREATE OR ALTER PROCEDURE dbo.SP_MonitorearCrecimientoLog
    @UmbralPorcentaje DECIMAL(5,2) = 80.0
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @NombreBD      SYSNAME = DB_NAME();
    DECLARE @PorcentajeUso DECIMAL(5,2);
    DECLARE @TamanioMB     DECIMAL(18,2);
    DECLARE @UsoMB         DECIMAL(18,2);
    DECLARE @Asunto        NVARCHAR(200);
    DECLARE @Cuerpo        NVARCHAR(MAX);

    SELECT
        @PorcentajeUso = used_log_space_in_percent,
        @UsoMB         = used_log_space_in_bytes / 1048576.0
    FROM sys.dm_db_log_space_usage;

    SELECT @TamanioMB = size * 8.0 / 1024
    FROM sys.database_files
    WHERE type_desc = 'LOG';

    IF @PorcentajeUso >= @UmbralPorcentaje
    BEGIN
        SET @Asunto = CONCAT(N'ALERTA: Log de ', @NombreBD, N' al ', @PorcentajeUso, N'%');
        SET @Cuerpo = CONCAT(
            N'El archivo de log de la base de datos ', @NombreBD,
            N' ha alcanzado ', @PorcentajeUso, N'% de uso.', CHAR(13)+CHAR(10),
            N'Tamaño total del log: ', @TamanioMB, N' MB.', CHAR(13)+CHAR(10),
            N'Espacio actualmente usado: ', @UsoMB, N' MB.'
        );

        EXEC msdb.dbo.sp_send_dbmail
            @profile_name = 'PerfilMonitoreo',
            @recipients   = 'dba@empresa.com',
            @subject      = @Asunto,
            @body         = @Cuerpo,
            @body_format  = 'TEXT';
    END;
END;
GO

-- Job de Agent: revisión cada 15 minutos
EXEC msdb.dbo.sp_add_job @job_name = N'Job_MonitoreoLog';
EXEC msdb.dbo.sp_add_jobstep
    @job_name = N'Job_MonitoreoLog',
    @step_name = N'Revisar crecimiento del log',
    @subsystem = N'TSQL',
    @command = N'EXEC dbo.SP_MonitorearCrecimientoLog;',
    @database_name = N'GradosTitulos';
EXEC msdb.dbo.sp_add_schedule
    @schedule_name = N'Cada15Min',
    @freq_type = 4,
    @freq_subday_type = 4,
    @freq_subday_interval = 15;
EXEC msdb.dbo.sp_attach_schedule @job_name = N'Job_MonitoreoLog', @schedule_name = N'Cada15Min';
EXEC msdb.dbo.sp_add_jobserver @job_name = N'Job_MonitoreoLog';
GO
3 Justificación técnica

sys.dm_db_log_space_usage expone el porcentaje de uso del log directamente desde el motor, sin necesidad de escanear el archivo físico, y es la vista recomendada frente a la sentencia heredada DBCC SQLPERF(LOGSPACE). sys.database_files aporta el tamaño físico configurado en páginas (que se convierte a MB multiplicando por 8/1024). El umbral se parametriza en lugar de codificarse fijo, y la alerta solo se dispara condicionalmente (IF @PorcentajeUso >= @UmbralPorcentaje), evitando saturar la bandeja de correo con notificaciones en cada ejecución del job.

4 Explicación de las buenas prácticas utilizadas
  • Uso de DMVs en vez de comandos DBCC heredados para obtener métricas en tiempo real.
  • Umbral configurable como parámetro del procedimiento, no como valor fijo dentro de la lógica.
  • Envío de alerta condicional, para que el correo sea una excepción y no una constante.
  • Frecuencia de revisión corta (15 min) frente al informe diario, acorde a la criticidad de quedarse sin espacio en el log.
  • Separación entre "tamaño configurado" y "espacio usado", permitiendo diagnosticar tanto crecimiento como falta de mantenimiento (backups de log).
Qué observa este proyecto
% uso del log ≥ 80% Frecuencia: cada 15 min Canal de salida: correo (Database Mail)

Ranking de rendimiento de procedimientos almacenados

Tablas de monitoreo DMV Procedimientos Consultas de rendimiento
1 Enunciado del ejercicio
Implementar un sistema que registre automáticamente el tiempo de ejecución de los procedimientos almacenados principales de la base de datos y genere un ranking de rendimiento.
2 Script en T-SQL
Ranking_Rendimiento_SP.sql
-- Tabla histórica de rendimiento
CREATE TABLE dbo.MonitoreoRendimientoSP
(
    Id              BIGINT IDENTITY(1,1) PRIMARY KEY,
    NombreSP        NVARCHAR(256)  NOT NULL,
    FechaEjecucion  DATETIME2      NOT NULL DEFAULT SYSDATETIME(),
    DuracionMs      BIGINT         NOT NULL,
    LecturasLogicas BIGINT         NULL,
    TiempoCPUMs     BIGINT         NULL
);
GO

-- Snapshot periódico desde la DMV de estadísticas de procedimientos
CREATE OR ALTER PROCEDURE dbo.SP_RegistrarRendimiento
AS
BEGIN
    SET NOCOUNT ON;

    INSERT INTO dbo.MonitoreoRendimientoSP (NombreSP, DuracionMs, LecturasLogicas, TiempoCPUMs)
    SELECT
        OBJECT_SCHEMA_NAME(ps.object_id, ps.database_id) + '.' + OBJECT_NAME(ps.object_id, ps.database_id),
        ps.total_elapsed_time / 1000,
        ps.total_logical_reads,
        ps.total_worker_time / 1000
    FROM sys.dm_exec_procedure_stats ps
    WHERE ps.database_id = DB_ID();
END;
GO

-- Ranking de rendimiento sobre los últimos 7 días
CREATE OR ALTER PROCEDURE dbo.SP_RankingRendimiento
    @TopN INT = 10
AS
BEGIN
    SET NOCOUNT ON;

    SELECT TOP (@TopN)
        NombreSP,
        AVG(DuracionMs)  AS PromedioDuracionMs,
        MAX(DuracionMs)  AS MaximoDuracionMs,
        COUNT(*)         AS Muestras
    FROM dbo.MonitoreoRendimientoSP
    WHERE FechaEjecucion >= DATEADD(DAY, -7, SYSDATETIME())
    GROUP BY NombreSP
    ORDER BY PromedioDuracionMs DESC;
END;
GO

-- Job de Agent: snapshot cada hora
EXEC msdb.dbo.sp_add_job @job_name = N'Job_SnapshotRendimiento';
EXEC msdb.dbo.sp_add_jobstep
    @job_name = N'Job_SnapshotRendimiento',
    @step_name = N'Registrar rendimiento',
    @subsystem = N'TSQL',
    @command = N'EXEC dbo.SP_RegistrarRendimiento;',
    @database_name = N'GradosTitulos';
EXEC msdb.dbo.sp_add_schedule
    @schedule_name = N'CadaHora',
    @freq_type = 4,
    @freq_subday_type = 8,
    @freq_subday_interval = 1;
EXEC msdb.dbo.sp_attach_schedule @job_name = N'Job_SnapshotRendimiento', @schedule_name = N'CadaHora';
EXEC msdb.dbo.sp_add_jobserver @job_name = N'Job_SnapshotRendimiento';
GO
3 Justificación técnica

sys.dm_exec_procedure_stats acumula, por procedimiento, el tiempo transcurrido, las lecturas lógicas y el tiempo de CPU desde la última recompilación o reinicio del servicio, sin necesidad de instrumentar manualmente cada SP existente. Como esta DMV se reinicia con recompilaciones o un restart del servicio, se toma un snapshot periódico hacia una tabla histórica propia, lo que permite conservar tendencias en el tiempo. El ranking agrega por procedimiento sobre una ventana móvil de 7 días usando AVG y MAX, dando visibilidad tanto del comportamiento típico como del peor caso.

4 Explicación de las buenas prácticas utilizadas
  • Monitoreo no intrusivo: no se modifica el código de los procedimientos monitoreados.
  • Separación entre captura (SP_RegistrarRendimiento) y consulta/reporte (SP_RankingRendimiento).
  • Ventana móvil de 7 días en el ranking en vez de un histórico acumulado completo, para reflejar el rendimiento reciente.
  • Parámetro @TopN configurable en el ranking, evitando resultados fijos o excesivos.
  • Filtro por DB_ID() para evitar mezclar estadísticas de procedimientos de otras bases del mismo servidor.
Qué observa este proyecto
Duración, lecturas y CPU por SP Frecuencia: snapshot cada hora Salida: ranking Top-N (7 días)

Sistema integral de monitoreo — base de datos GradosTitulos

Bloqueos Consultas lentas Sesiones con alto CPU Tablas históricas Alertas por correo Informe diario
1 Enunciado del ejercicio
Desarrollar un sistema integral de monitoreo para la base de datos GradosTitulos que realice automáticamente:
  • Monitoreo de bloqueos (blocking)
  • Detección de consultas lentas
  • Identificación de sesiones con alto consumo de CPU
  • Registro de eventos en tablas históricas
  • Envío de alertas por correo cuando se superen umbrales establecidos
  • Generación diaria de un informe consolidado del estado del servidor
El script integra Transact-SQL, SQL Server Agent, Dynamic Management Views (DMV), Database Mail (sp_send_dbmail), TRY...CATCH, transacciones, tablas de auditoría e historial, y procedimientos almacenados para automatizar el monitoreo y la generación de reportes.
2 Script en T-SQL
Monitoreo_Integral_GradosTitulos.sql
USE GradosTitulos;
GO

/* ============ 1. TABLAS HISTÓRICAS ============ */

CREATE TABLE dbo.MonitoreoBloqueos
(
    Id                  BIGINT IDENTITY(1,1) PRIMARY KEY,
    FechaDeteccion      DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    SesionBloqueada     INT NOT NULL,
    SesionBloqueadora   INT NOT NULL,
    ConsultaBloqueada   NVARCHAR(MAX) NULL,
    EsperaMs            BIGINT NULL
);
GO

CREATE TABLE dbo.MonitoreoConsultasLentas
(
    Id              BIGINT IDENTITY(1,1) PRIMARY KEY,
    FechaDeteccion  DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    TextoConsulta   NVARCHAR(MAX) NULL,
    DuracionMs      BIGINT NOT NULL,
    LecturasLogicas BIGINT NULL,
    SesionId        INT NULL
);
GO

CREATE TABLE dbo.MonitoreoSesionesCPU
(
    Id              BIGINT IDENTITY(1,1) PRIMARY KEY,
    FechaDeteccion  DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    SesionId        INT NOT NULL,
    LoginName       NVARCHAR(128) NULL,
    CPUTimeMs       BIGINT NULL,
    ProgramName     NVARCHAR(256) NULL
);
GO

CREATE TABLE dbo.LogEventosMonitoreo
(
    Id           BIGINT IDENTITY(1,1) PRIMARY KEY,
    Fecha        DATETIME2 NOT NULL DEFAULT SYSDATETIME(),
    Proceso      NVARCHAR(128) NOT NULL,
    Mensaje      NVARCHAR(MAX) NOT NULL,
    Severidad    VARCHAR(20) NOT NULL DEFAULT 'INFO'
);
GO

/* ============ 2. DETECCIÓN DE BLOQUEOS ============ */

CREATE OR ALTER PROCEDURE dbo.SP_DetectarBloqueos
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRY
        INSERT INTO dbo.MonitoreoBloqueos (SesionBloqueada, SesionBloqueadora, ConsultaBloqueada, EsperaMs)
        SELECT
            r.session_id,
            r.blocking_session_id,
            st.text,
            r.wait_time
        FROM sys.dm_exec_requests r
        CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) st
        WHERE r.blocking_session_id <> 0;
    END TRY
    BEGIN CATCH
        INSERT INTO dbo.LogEventosMonitoreo (Proceso, Mensaje, Severidad)
        VALUES ('SP_DetectarBloqueos', ERROR_MESSAGE(), 'ERROR');
    END CATCH
END;
GO

/* ============ 3. DETECCIÓN DE CONSULTAS LENTAS ============ */

CREATE OR ALTER PROCEDURE dbo.SP_DetectarConsultasLentas
    @UmbralMs INT = 5000
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRY
        INSERT INTO dbo.MonitoreoConsultasLentas (TextoConsulta, DuracionMs, LecturasLogicas, SesionId)
        SELECT
            st.text,
            r.total_elapsed_time,
            r.logical_reads,
            r.session_id
        FROM sys.dm_exec_requests r
        CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) st
        WHERE r.total_elapsed_time >= @UmbralMs
          AND r.session_id <> @@SPID;
    END TRY
    BEGIN CATCH
        INSERT INTO dbo.LogEventosMonitoreo (Proceso, Mensaje, Severidad)
        VALUES ('SP_DetectarConsultasLentas', ERROR_MESSAGE(), 'ERROR');
    END CATCH
END;
GO

/* ============ 4. SESIONES CON ALTO CONSUMO DE CPU ============ */

CREATE OR ALTER PROCEDURE dbo.SP_DetectarSesionesAltoCPU
    @UmbralCPUMs INT = 10000
AS
BEGIN
    SET NOCOUNT ON;
    BEGIN TRY
        INSERT INTO dbo.MonitoreoSesionesCPU (SesionId, LoginName, CPUTimeMs, ProgramName)
        SELECT
            session_id,
            login_name,
            cpu_time,
            program_name
        FROM sys.dm_exec_sessions
        WHERE cpu_time >= @UmbralCPUMs
          AND is_user_process = 1;
    END TRY
    BEGIN CATCH
        INSERT INTO dbo.LogEventosMonitoreo (Proceso, Mensaje, Severidad)
        VALUES ('SP_DetectarSesionesAltoCPU', ERROR_MESSAGE(), 'ERROR');
    END CATCH
END;
GO

/* ============ 5. ALERTAS POR CORREO (umbral superado) ============ */

CREATE OR ALTER PROCEDURE dbo.SP_EnviarAlertasCriticas
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @Cuerpo    NVARCHAR(MAX);
    DECLARE @Bloqueos  INT, @Lentas INT, @CPU INT;

    SELECT @Bloqueos = COUNT(*) FROM dbo.MonitoreoBloqueos        WHERE FechaDeteccion >= DATEADD(MINUTE,-15,SYSDATETIME());
    SELECT @Lentas   = COUNT(*) FROM dbo.MonitoreoConsultasLentas WHERE FechaDeteccion >= DATEADD(MINUTE,-15,SYSDATETIME());
    SELECT @CPU      = COUNT(*) FROM dbo.MonitoreoSesionesCPU     WHERE FechaDeteccion >= DATEADD(MINUTE,-15,SYSDATETIME());

    IF @Bloqueos > 0 OR @Lentas > 0 OR @CPU > 0
    BEGIN
        SET @Cuerpo = CONCAT(
            N'Resumen de incidencias (últimos 15 min):', CHAR(13)+CHAR(10),
            N'- Bloqueos: ', @Bloqueos, CHAR(13)+CHAR(10),
            N'- Consultas lentas: ', @Lentas, CHAR(13)+CHAR(10),
            N'- Sesiones con alto CPU: ', @CPU
        );

        BEGIN TRY
            EXEC msdb.dbo.sp_send_dbmail
                @profile_name = 'PerfilMonitoreo',
                @recipients   = 'dba@empresa.com',
                @subject      = N'Alerta de monitoreo - GradosTitulos',
                @body         = @Cuerpo,
                @body_format  = 'TEXT';
        END TRY
        BEGIN CATCH
            INSERT INTO dbo.LogEventosMonitoreo (Proceso, Mensaje, Severidad)
            VALUES ('SP_EnviarAlertasCriticas', ERROR_MESSAGE(), 'ERROR');
        END CATCH
    END;
END;
GO

/* ============ 6. INFORME DIARIO CONSOLIDADO ============ */

CREATE OR ALTER PROCEDURE dbo.SP_InformeDiarioConsolidado
AS
BEGIN
    SET NOCOUNT ON;
    DECLARE @Cuerpo NVARCHAR(MAX);

    SELECT @Cuerpo = CONCAT(
        N'Informe diario de monitoreo - ', CONVERT(VARCHAR(20), GETDATE(), 103), CHAR(13)+CHAR(10), CHAR(13)+CHAR(10),
        N'Bloqueos detectados: ',   (SELECT COUNT(*) FROM dbo.MonitoreoBloqueos        WHERE CAST(FechaDeteccion AS DATE) = CAST(GETDATE() AS DATE)), CHAR(13)+CHAR(10),
        N'Consultas lentas: ',      (SELECT COUNT(*) FROM dbo.MonitoreoConsultasLentas WHERE CAST(FechaDeteccion AS DATE) = CAST(GETDATE() AS DATE)), CHAR(13)+CHAR(10),
        N'Sesiones con alto CPU: ', (SELECT COUNT(*) FROM dbo.MonitoreoSesionesCPU     WHERE CAST(FechaDeteccion AS DATE) = CAST(GETDATE() AS DATE)), CHAR(13)+CHAR(10),
        N'Errores del propio sistema de monitoreo: ', (SELECT COUNT(*) FROM dbo.LogEventosMonitoreo WHERE Severidad = 'ERROR' AND CAST(Fecha AS DATE) = CAST(GETDATE() AS DATE))
    );

    BEGIN TRY
        EXEC msdb.dbo.sp_send_dbmail
            @profile_name = 'PerfilMonitoreo',
            @recipients   = 'dba@empresa.com',
            @subject      = N'Informe diario - GradosTitulos',
            @body         = @Cuerpo,
            @body_format  = 'TEXT';
    END TRY
    BEGIN CATCH
        INSERT INTO dbo.LogEventosMonitoreo (Proceso, Mensaje, Severidad)
        VALUES ('SP_InformeDiarioConsolidado', ERROR_MESSAGE(), 'ERROR');
    END CATCH
END;
GO

3 Justificación técnica

El sistema combina varias DMVs complementarias: sys.dm_exec_requests expone tanto bloqueos (vía blocking_session_id) como duración de ejecución en curso, sys.dm_exec_sql_text resuelve el texto real de la consulta a partir del sql_handle, y sys.dm_exec_sessions aporta el consumo acumulado de CPU por sesión. Cada tipo de incidencia se persiste en su propia tabla histórica, lo que permite análisis forense posterior y evita perder información cuando las DMVs se reinician. Las alertas se separan de la detección: la detección corre cada 5 minutos y solo dispara correo si hay incidencias en los últimos 15 minutos, mientras que el informe diario agrega el panorama completo del día anterior. Cada paso del job de detección continúa aunque uno falle (on_success_action = 3: ir al siguiente paso), evitando que un fallo puntual detenga todo el pipeline de monitoreo.

4 Explicación de las buenas prácticas utilizadas
  • Separación de responsabilidades: detección, alertamiento y reporte son procedimientos independientes que pueden programarse con frecuencias distintas.
  • Todo procedimiento de detección envuelve su lógica en TRY/CATCH y registra sus propios fallos en LogEventosMonitoreo, de modo que el sistema de monitoreo audita también sus propios errores.
  • Umbrales configurables como parámetros (@UmbralMs, @UmbralCPUMs) en lugar de valores fijos en el cuerpo del procedimiento.
  • Uso de CROSS APPLY con sys.dm_exec_sql_text para obtener el texto de la consulta de forma eficiente, sin necesidad de habilitar trazas adicionales.
  • Ventanas de tiempo acotadas (15 minutos para alertas, día calendario para el informe) para que cada consulta sea liviana y no escanee el histórico completo.
  • Jobs de Agent independientes por función, permitiendo ajustar la frecuencia de cada uno sin afectar a los demás.
